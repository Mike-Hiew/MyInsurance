## System Vision

A health-insurance reimbursement claim travels from photographed documents to a payment decision without a person re-keying anything. BnK IDP reads the documents, a group of agents on ODC Agent Workbench interprets and recommends, a deterministic Server Action chain computes every amount, and a claim officer confirms only what needs human judgement. The customer sees a plain-language result explaining what they must pay themselves and why.

This document coordinates **two Mentor-generated apps**. It does not restate the business case — that lives in `03-BRD-Context-AgenticHealthClaim-2026-09-15.md` — and it does not replace `BRD_Agentic_Health_Claim_Adjudication_v1.0.md`, which remains the full functional baseline.

### What happens to ClaimMVP

Generating a fresh data model means the 13 entities on `ClaimMVP` are no longer the ones the console displays. Its Server Actions therefore write to entities nothing reads. The consequence is deliberate and has a cost: **the 14-step adjudication chain, the auto-approval gate, the limit-ledger posting and the six IDP REST methods must be rebuilt inside `ClaimConsole`.** Mentor does not generate any of them.

`ClaimMVP` stays on the tenant as working reference code — particularly for the IDP integration, where the Cloudflare `User-Agent` requirement, errors returned inside HTTP 200, and the `recommendations = []` trap are already solved. Port that code rather than rediscovering it.

## Cross-App Dependencies

- `ClaimPortal` cannot be generated until `ClaimConsole` exists and its entities are **exposed as public**. Mentor does not set that flag; do it in ODC Studio between the two generations.
- `ClaimPortal` has no logic of its own. Every amount it shows is written by `ClaimConsole`, so a figure is never computed twice and the member and the officer cannot disagree.
- The agent layer depends on `ClaimConsole` only through its entities and Server Actions. Nothing in this BRD set asks Mentor to create, modify or wire an agent.
- Nothing depends on `ClaimMVP` at runtime. If it is later deleted, no part of this system breaks.

## Success Criteria (System-Level)

- A claim submitted in `ClaimPortal` appears in the `ClaimConsole` worklist with documents read by real IDP.
- The officer sees per-line agent recommendations with evidence and can confirm or reject each one with a mandatory reason.
- Every amount on screen traces to a `ChainRun` row that can be re-run and produce the identical figure.
- Every agent hand-off is visible as an `AgentRun` row with `HandoffTo` populated.
- The customer result screen and the officer settlement screen show the same numbers.

## Recommended Build Order

1. **`ClaimConsole` first** — it owns the data model, so nothing else can reference entities until it is generated and reviewed.
2. **Expose entities as public**, in ODC Studio. Mentor does not set this.
3. **`ClaimPortal` second**, referencing those public entities rather than generating its own.
4. **Port the IDP REST consume** from `ClaimMVP` into `ClaimConsole`. Copy it rather than rewriting — the three known traps are already handled there.
5. **Rebuild the deterministic core** inside `ClaimConsole`: `RunAdjudicationChain`, `EvaluateAutoApprovalGate`, the limit-ledger posting. This is the largest hand-built item and the one Mentor contributes nothing to. Start it as soon as the blueprint is confirmed, in parallel with step 3.
6. **Remove update and delete** from the append-only entities Mentor will have given full CRUD: `AgentRun`, `ClaimEvent`, and `ClaimDocument.RawExtractionJson`.
7. **Agent layer last**, in Agent Workbench, against a data model that has stopped moving.

The critical path is step 5, not the generation. Sequence the sprint around it.
