## Executive Summary

A health reimbursement claim today is read by hand. An officer opens photographed discharge papers and itemised statements, re-keys cost lines, cross-checks them against the benefit tree in a separate system, applies waiting periods and caps, and writes a decision. The work is slow, and the part that actually needs a human — judging whether a line is medically related and covered — is buried under the part that does not.

This programme moves the mechanical work to software and leaves the judgement with people. An external extraction service reads the documents. A group of agents on ODC Agent Workbench interprets the extraction, proposes a reason code per cost line with supporting evidence, and drafts the member's letter. A deterministic Server Action chain computes every amount. The officer confirms or rejects proposals; the officer never re-keys.

The governing rule, and the reason the architecture looks as it does: **money is deterministic, judgement is agentic.** Every amount comes from a chain that can be re-run and produce the same figure. No agent holds a tool that writes a monetary field.

## Pre-Generation Checklist

These must be settled before either upload file is used. The first two are hard blockers.

1. **Accept that the deterministic core is rebuilt.** *Decided 15/09/2026: build fresh, do not derive from `ClaimMVP`.* The upload files tell Mentor to generate the data model as stored locally, using the tenant's attribute naming but not its entities. `ClaimMVP` is parked as reference code and nothing links to it at runtime. The cost this buys is real and is the largest single item in the remaining sprint: **the 14-step chain, the auto-approval gate, the limit-ledger posting and the six IDP REST methods must be rebuilt inside `ClaimConsole`.** Port the IDP code from `ClaimMVP` rather than rewriting it; the Cloudflare `User-Agent` requirement, errors returned inside HTTP 200, and the `recommendations = []` trap are already solved there.
2. **Expose `ClaimConsole` entities as public** once it is generated. `ClaimPortal` cannot reference anything until that is done, and Mentor does not set the flag.
3. **Confirm the static entity records.** The `Records:` lines for `ClaimStatus`, `PolicyStatus`, `TreatmentType` and `DecisionCode` were derived from the design documents, **not read from the tenant** — the available tooling exposes static entity structure but not its rows without standing up a test harness. Open these four static entities in ODC Studio and correct the record lists before generating.
4. **Seed data must be synthetic.** Rule BC-1 stands: no real member name, date of birth, health card number or bank account reaches the tenant. The upload files contain attribute names only and no sample values, which is what Mentor's own guidance requires.

## Data Type Translation

Mentor's requirement-document vocabulary has nine attribute types and **Decimal is not among them**. The tenant uses Decimal in three places, so the upload files translate as follows. Each translation is a real change, not a formatting choice.

| Tenant | Upload file | Consequence |
|---|---|---|
| `Decimal(18,0)` for money | `Currency` | Correct and intended. ODC generates the right field and validation. |
| `Decimal(37,8)` for `Confidence` | `Integer`, 0 to 100 | **Deviates from rule DR-03**, which stores confidence as 0–1. Either accept percent storage, or change the type back in ODC Studio after generation and adjust the extraction adapter. |
| `Decimal(37,8)` for `CoinsurancePct` | `Integer`, 0 to 100 | Acceptable for whole-percent coinsurance. If fractional percentages are ever needed, change the type in Studio. |
| `Long Integer` identifiers | `Identifier` | No practical difference; ODC generates Long Integer identifiers anyway. |

## Non-Functional Requirements

- **Auditability.** `AgentRun`, `ClaimEvent` and `RawExtractionJson` are append-only. Generated CRUD screens must not expose update or delete on these; remove those actions after generation.
- **Reproducibility.** Any two runs of the adjudication chain over identical inputs produce identical totals. `ChainRun.InputsHash` exists so a screen can tell whether displayed amounts are stale after an edit.
- **Extraction latency.** The external service takes roughly 16 seconds per page. Screens must show progress rather than block.
- **Resilience.** An extraction failure moves the claim to Extraction Error and into the operator queue. A claim is never declined automatically because a document could not be read.
- **Privacy.** Payout accounts and national identifiers are stored masked. No unmasked identifier exists in the demonstration tenant.

## Acceptance Criteria

| Scenario | Criteria |
|---|---|
| **B — clean claim** | Member submits from the portal; documents are read by the real extraction service; the chain computes a payable amount; the auto-approval gate passes on all four conditions; the member sees the result with the same totals the officer sees. |
| **A — clinical recommendation** | A cost line receives a not-covered proposal with evidence and a confidence band; the officer rejects it with a reason; the chain re-runs; the new total differs from the first and both runs remain visible. |
| **D — waiting period decline** | A claim whose event date falls inside the waiting period is declined; the member's result screen shows the amount borne grouped under the waiting-period cause with the approved wording. |
| **Agent hand-off** | For any of the above, the agent trace shows more than one agent with `HandoffTo` populated, in time order, with durations. |

## Dependencies & Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Agent Workbench does not permit an agent to call another agent | The agent-to-agent story, which the judging favours, weakens | Orchestrator becomes a Server Action; hand-offs still written to `AgentRun`, so the trace and narrative survive |
| Rebuilding the chain does not finish before the pitch | The demonstration has screens but no correct amount, which is the whole claim | Accepted consequence of building fresh. Start the chain the day the blueprint is confirmed, not after the screens are polished. Fall back to scenario B only, per the existing cut list |
| Two schemas coexist on the tenant during the sprint | Seed data written to the wrong copy; confusion over which app to open | Park `ClaimMVP` explicitly — stop publishing to it the day `ClaimConsole` is generated, and reseed demo data into `ClaimConsole` only |
| Extraction service unavailable during the pitch | No live document read | `IdpReplay` holds recorded responses; replay mode runs the full flow with a genuine `AgentRun` trace |
| Blueprint drifts from this specification | Silent substitution of UI patterns or attributes | Mentor output is non-deterministic by design. Review the blueprint against these files before confirming generation, and iterate by follow-up prompt rather than by hand-editing |
| Static entity records wrong | State machine allows invalid transitions | Checklist item 3 |

## Success Metrics

| Measure | Baseline | Target |
|---|---|---|
| Officer handling time per claim | Manual re-keying of every cost line | Confirm or reject proposals only |
| Straight-through processing rate | Zero | Clean claims approved without officer touch |
| Amount traceability | Spreadsheet working | Every amount traces to a re-runnable `ChainRun` |
| Decision explainability | Free-text notes | Per-cause breakdown with approved wording, identical in console and portal |

Figures for the pitch should come from `AccuracyRun` and measured timings, and every ROI input shown to judges should be labelled as an assumption where it is one.
